## 问题与建议优先级

P1 表示直接妨碍日常闭环，P2 表示明显摩擦或控制语义不一致；不是安全漏洞严重度。本轮没有确认数据丢失或越权泄露。

### M1 · P1 · 无法确认完成或归档，待核对事项持续积累

- 复现：生成 D1 成果，查看、核对后尝试结束事项；到 D5 查看首页。
- 实际：只有复制、纠正、补资料及运行记录；没有“已核对”“完成”“归档”。D1、D3、D3b 共三项仍为 `ready / 待你核对`。
- 影响：用户没有办法表达“这件事已经处理好了”。首页无法区分未读交付、已采纳成果和已完成事项。
- 原因：[WorkbenchV2.tsx](../../src/components/WorkbenchV2.tsx) 第 16、156、160–164 行只有运行/成果状态；[事项 API](../../src/app/api/work-items/route.ts) 没有接收、完成或归档操作。
- 建议：区分运行结束、成果待确认、事项完成，提供可恢复的完成/归档操作与历史查看。不要删除原成果。
- 验证目标：D1 完成后退出待处理区，D5 仍能从历史查看和重新打开。

### M2 · P1 · 新版学习事项在生成文本后停止，没有作答与反馈的接续流程

- 复现：D3 请求“围绕周末生活，一次问一个问题，等我作答后点评，再决定下一题”，开始运行后尝试回答。
- 实际：得到成果面板，“继续协作”因当前修订已就绪而禁用；可输入的只有纠正和资料。无法自然提交本题答案、获得反馈并进入下一题。
- 影响：多天学习需要把回答伪装成纠正或反复修改资料，系统也缺少明确的练习完成和学习进展记录。
- 原因：[WorkbenchV2.tsx](../../src/components/WorkbenchV2.tsx) 第 160–164 行以“生成—纠正—再生成”为唯一新事项后续路径；[workflow.ts](../../src/lib/workflow.ts) 第 34–38 行主要按成品交付定义角色输出。
- 边界：旧版 `/legacy` 有练习与反馈功能，不能说整个项目没有；缺的是它与新版持续事项的连接。本结论不依赖 mock 是否生成了合格问题。
- 建议：保留一次性交付，并给学习事项增加“开始练习 → 提交回答 → 反馈 → 下一步”的最小流程，引用原事项与历史表现。
- 验证目标：同一事项跨两日练习，能看见上一轮答案和反馈，并明确下一轮采用了什么依据。

### M3 · P1 · 首页遗漏真正需要介入的受阻与中断事项

- 复现：D4 暂停英语，让中文成功而英语待继续；D5 重启应用，使未结束运行恢复为中断；分别回首页。
- 实际：“需要你参与”只有另外两个 `ready` 项，未纳入 `waiting` 或 `interrupted` 的 D1。
- 影响：这些状态必须由用户恢复角色或手动继续，首页却不提醒。D1 当时还能从“最新事项”和侧栏找到，但更新其他事项后更容易被埋没。
- 原因：[WorkbenchV2.tsx](../../src/components/WorkbenchV2.tsx) 第 156 行仅筛选 `ready` 和 `failed`，且最多展示三项。`cancelled` 同样被代码排除，但用户主动取消不应无条件当作告警。
- 建议：按所需动作归类待办，纳入中断和受阻，说明原因并给出恢复入口；主动取消可另列为可恢复历史。
- 验证目标：生成新事项后，中断旧事项仍能从首页待处理入口找到；已完成事项不占待处理位。

### M4 · P2 · 轻微约束变化使全部成果失效，时间协调缺少可执行安排

- 复现：D2 保持资料与需求不变，仅把 D1 从 45 分钟改成 20 分钟。
- 实际：修订 2 变为 3，中文和英文均从当前成果降为“待更新”；D4 必须重新生成中文 v3、英文 v3 才恢复就绪。旧版本可查，没有丢失。
- 实际：分工页将参与分钟数字换为 20，没有提供如何压缩练习或优先核对哪些内容的具体安排。时间确实被传给模型，不能据此断言真实模型绝不会调整输出。
- 另一实例：D4 仅要求英文介绍控制在一分钟，也使中文和英文一起待更新。
- 原因：[work-items.ts](../../src/lib/work-items.ts) 第 99–118 行对资料、时间、优先级和纠正统一递增事项修订；第 13–16 行 [workflow.ts](../../src/lib/workflow.ts) 要求所有成果匹配该修订。优先级变化同样失效由代码确认，本轮未单独从 UI 改优先级。
- 影响：用户只是改变自己的参与时间，也要重新支付两次生成成本；成果内容修订和用户安排调整混在一起。
- 建议：区分事实/成品要求变更与参与安排变更，标记受影响的角色和成果；重新生成前解释原因。先做单事项内的具体取舍，不直接扩建复杂日历。
- 验证目标：缩短练习时间仍能阅读已核对成果，并得到具体安排；只修改英文表达时能说明是否确实需要重做中文。

### M5 · P2 · 协调员暂停与新版分工展示不一致

- 复现：D4 在团队页暂停日程协调员、恢复英语；继续 D1，D5 再运行修订 4。
- 实际：团队显示协调员暂停；新版仍显示“日程协调员按所选角色和时间生成透明分工”，允许执行中文、英文，协调员参与事项统计为 0。最终数据库确认其 enabled 为 0。
- 原因：[WorkbenchV2.tsx](../../src/components/WorkbenchV2.tsx) 第 140、159、166 行和 [workflow.ts](../../src/lib/workflow.ts) 第 70–74、89 行仅把领域角色纳入执行控制；规则分工不读取协调员状态。
- 边界：规则协调本身合理，也不要求每个角色都调用 LLM；问题是界面将它表现为可暂停、正在参与的角色，却没有对应行为。旧版协调控制不同，不能笼统说暂停全部失效。
- 建议：明确它是不可独立暂停的系统编排能力，或定义暂停后停止哪些新分工动作并兑现；不要显示无效控制。
- 验证目标：暂停后的行为、团队统计与事项中的角色说明一致。

### M6 · P2 · 保存事项后无法更改需求与参与角色

- 复现：D3 保存买菜清单事项，未选领域角色；D5 在本事项资料补充“请英语教练把采购清单翻译成英文：鸡蛋、牛奶、番茄”，保存。
- 实际：修订升为 2，仍为范围外且没有运行入口；详情页没有调整参与角色的控制。可行绕路是重新创建英语事项，原事项上下文与历史无法自然延续。
- 原因：[事项 API](../../src/app/api/work-items/route.ts) 第 26–28 行和 [work-items.ts](../../src/lib/work-items.ts) 第 99–107 行只允许更改资料、时间、优先级。
- 边界：不应让添加资料自动授权新角色；缺的是用户显式修改和确认分工的入口。
- 建议：提供“修改需求/调整分工”，显示新增角色将读取的资料范围，按影响保留或更新已有成果。
- 验证目标：同一事项能从范围外转为英语协作，不必复制新建；运行中的修改受控，旧来源可查。

- 延伸观察：点击“完成事项”可以直接完成，没有提示尚有一道待答题；重新打开后该题仍在，未发生数据丢失。用户有权放弃练习，因此不建议一律禁止完成，而应说明未完工作并允许明确结束。
- 原因：[WorkbenchV2.tsx](../../src/components/WorkbenchV2.tsx) 第 22–31 行 `nextAction` 只判断 `rounds[0]`，没有按角色汇总待答、失败和中断；[work-items.ts](../../src/lib/work-items.ts) 第 282–294 行的完成条件只检查无模型运行及成果已确认。
- 影响：多 Agent 的状态被压缩成最新一条动态，用户容易遗漏另一角色的行动；这是旧 M3 提醒修复后仍未覆盖的组合场景。
- 建议：按所有当前角色的有效轮次汇总待处理动作，优先显示失败/中断和待答，再展示已完成反馈。完成事项前说明仍有几轮未完，可选择结束或继续。
- 复验标准：一个角色待答、另一个反馈完成时，首页明确显示待答角色和入口；完成动作的未完事项语义清晰。

### RT2 · P2 · 暂停角色后练习按钮仍可用，点击才报错

- 复现：生活翻译事项已生成英语成果，在团队页暂停英语，回事项点击“开始练习”。
- 实际：按钮正常可点，点击后才显示“参与角色已暂停，请先恢复”。本次没有产生练习运行或模型调用，后端控制有效。
- 原因：[WorkbenchV2.tsx](../../src/components/WorkbenchV2.tsx) 第 251 行练习开始、提交、恢复按钮没有按对应角色的 enabled 状态禁用；[practice.ts](../../src/lib/practice.ts) 在请求执行时才拒绝。
- 建议：练习区域展示该角色已暂停，禁用不可执行的动作并给出恢复入口，与成果协作的暂停反馈保持一致。
- 复验标准：暂停后无需先点击报错便能理解原因；恢复后按钮可用，暂停状态不发起模型调用。

### RT3 · P3 · 新成果已更新，旧练习仍提示先更新成果

- 复现：完成英文 v1 的练习后，修改英文补充要求并成功生成 v2。
- 实际：v2 明确标为当前成果，“开始下一轮练习”可用，但旧轮次旁仍显示“本轮题目依据的成果已过期……请先更新成果，再开始新一轮练习”。用户刚完成更新，提示与当前状态矛盾。
- 原因：[WorkbenchV2.tsx](../../src/components/WorkbenchV2.tsx) 第 251 行只要旧轮次来源不同于当前成果就展示同一提示，没有区分“尚无有效新成果”和“新成果已经就绪”。
- 建议：新成果已就绪时改为“此轮基于旧版本，已保留；下一轮将使用 v2”，仅在当前成果确实缺失时要求更新。
- 复验标准：未生成新成果和新成果已生成两种状态给出不同且可执行的指引。

### 发现及产品影响

1. **P1 · 暂停/恢复使开放事项中未改内容的既有成果失效。**D1 生活 v1 已成功，D5 仅暂停该实例后，隔离页面的 D1 详情显示“当前配置或资料下尚无有效成果”、历史 1 份，首页要求先恢复；D6 恢复后仍没有当前成果，D7 须额外调用得到 v2 才能核对完成。`setProfileEnabled` 每次切换都递增实例修订，而 `stepInput` 的成果哈希包含该修订；`currentArtifact` 因哈希变化排除旧成果。结果没有丢失，但用户为纯状态切换承担重复调用和多项待办。范围是该实例参与的**开放事项**；已完成事项读取核对时快照，本轮未见其成果被改写。建议把启停门禁与会改变成果内容的配置修订分开，并在恢复后沿用未发生内容/权限变化的成果；保留运行中取消的保护。

2. **P2 · 自建学习 Agent 的跨日练习只具备文本事项流程。**D3 成果可保存，D4 同事项手动把请求改为“点评回答”后，新输入只有新的请求、回答文本和有效偏好；没有自动带入 D3 题目。用户必须复制题目或使用求职/英语快捷事项的专用练习入口。历史可查不等于下一轮自动读到历史。建议为自建学习事项设计显式的题目→作答→反馈→下一轮来源，或把现有练习能力接入通用 Agent；权限仍由用户选择。

3. **产品范围缺口 · 跨事项连续性依赖用户手工组织。**D5 同一生活 Agent 的新事项继承明确保存的偏好，却不会读取 D1 采购成果；这是当前事项级隔离规则的正确表现，不能把它报成越权或实现 bug。但用户想让助手“记得上次计划并继续调整”，目前只能自己引用/搬运，缺少按个人目标授权、可见来源的跨事项关联。七日事项总览按状态列出 6 项，没有长期目标或每周进展聚合；自定义事项也没有快捷事项的参与时间/优先级安排。建议先提供可明确选择的“沿用上次事项成果”与目标级进展，再考虑自动推荐；不要默认共享全部生活资料。

这轮模拟证明的是状态和资料流；没有真实用户七日行为、时间节省、学习进步或建议质量数据。无需据此否定已有 MVP：单事项多 Agent 协作已经可用，但“持续管理我的学习和生活”的承诺仍需要补上上述跨日接续。下一步先处理 P1，再以一个真实个人目标验证跨日学习和生活事项的接续价值。
